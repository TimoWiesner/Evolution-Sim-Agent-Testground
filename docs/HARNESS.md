# Harness engineering notes

- A run is identified by profile, track and run id and lives at `<runs_root>/<profile>/<track>/<run-id>/`, outside the benchmark repository. `run.json` records the resolved profile settings, CLI version, harness commit and host hardware. Resuming a run whose profile settings have changed is refused.
- Container isolation: one long-lived rootless Podman container per run (`evo-<profile>-<track>-<run-id>`), started on demand and stopped when `run` ends; each phase is a fresh `podman exec`. It is kept between invocations so agent-installed system packages usually survive; it is safe to delete (`podman rm`), the harness recreates it. Mounts: workspace at `/workspace`, `<run>/home` at `/root`, the host's CLI binary read-only under `/opt/evo-cli`. Network is `pasta` with the host mapping removed; `host_ports` forwards single host loopback ports (local model servers). The phase time limit is enforced by `timeout` inside the container. Validation, commits and acceptance checks run on the host.
- Hidden evaluation: after a task becomes DONE the harness exports that commit with `git archive`, runs `./setup.sh` and `./build.sh` in a fresh container (network on, tests absent), commits that container to a temporary image, and runs the private suite from it with `--network none` and the suite mounted read-only. Results go to `<run>/eval/<task>.json` and a summary into `state.json`; nothing is written to the workspace. Evaluation time is not counted as agent time.
- The next task is chosen by the harness in a fixed order (started tasks first, then lowest ready ID), never by the model.
- Parallel track: a thread pool of `workers` slots; every job is one phase or one merge of one task. Jobs are handed out in a fixed order: merges first (never two at once, they all write to the main workspace), then started tasks, then the lowest ready IDs. Shared state is guarded by one lock and written after every job. Interrupted phases leave `inflight-<task>.json`.
- Task checkouts are plain local clones (`<run>/workers/<task>`, origin removed), not `git worktree`s: a worktree's `.git` file stores an absolute host path that does not exist inside the container, and a clone keeps an agent away from the main repository's Git data. In the container they are mounted at `/workers`. A checkout is deleted after its merge; the task's commits stay reachable through the `--no-ff` merge commit. A blocked task keeps its checkout.
- A merge runs `git fetch <checkout> HEAD` and `git merge --no-ff --no-commit FETCH_HEAD` in the main workspace. On conflicts an agent call with phase `merge` runs there; the harness then requires a valid handoff, intact protected files, no `<<<<<<<`/`>>>>>>>` markers in the conflicted files, and that the task's commit is an ancestor of the result. On failure the workspace is reset to the commit before the merge. Merge calls are ordinary events (tokens, cost and time count); `state.json` also keeps one `merges` record per task.
- `elapsed_seconds` in `state.json` accumulates the wall-clock time of the parallel scheduling loop over all invocations. Hidden evaluations run in a separate single thread on the merge commit, with the list of done tasks as it was at that merge.

- Phase time limit: the profile's `phase_timeout_seconds` times the task's `timeout_factor` in `task.json` (2 for TASK-018, 019, 021, 022, 024, 025, 026, 027 and 028, which need long simulation runs, measurements or UI checks; 1 otherwise). The prompt states the limit in minutes so the agent can plan long runs.
- Each task phase gets a fresh CLI subprocess. All relevant context is loaded from workspace files and the explicit absolute handoff destination.
- OpenCode uses `--standalone` to avoid user-level shared daemon session association; the subprocess `cwd` identifies the workspace.
- Task descriptions and skill sources are copied from the operator package. Only benchmark-controlled immutable files are integrity-checked. Generated `handoffs/` files are excluded.
- JSON handoff is a required contractual artifact; missing / malformed files receive `HANDOFF_INVALID` rather than an uncaught `FileNotFoundError`.
- A per-run OS `flock` prevents two runs from mutating the same workspace simultaneously. The runner writes `inflight.json` before executing a phase and removes it after persistence.
- A phase commit is created after execution even when a phase fails; commit description includes the failure class. This preserves diagnostic file changes. On integrity violation the protected files are restored from operator copies before commit (incident recorded in the event).
- Recovery retries the **same phase** with new context; previous handoffs are archived. On exhaustion the task becomes `BLOCKED` and unlocked independent tasks can run.
- All CLI stdout JSONL streams to a file immediately; a small event filter shows succinct live activity. Raw logs are sensitive and should not be publicly shared unredacted.
- The generic acceptance script only checks minimum harness criteria. The benchmark is not yet a complete, independent scientific evaluation of simulation quality.
- CLI flags are version-sensitive. Verify on the installation under test with `claude --help`, `codex exec --help`, `opencode run --help` before a multi-day run.
- Subagent track: identical to sequential except for `DELEGATION_NOTE` in the prompt and Codex running without `--ephemeral` (with it every spawn fails with "no rollout found"; verified on codex-cli 0.164.0). Skills and starter files are the same in all tracks. Subagent use is read per phase into `usage.delegated` and `usage.subagents`: Claude from `subagent_stats.spawned` in the result event, Codex from the presence of `collab_tool_call` items (its JSON stream shows no spawn count), opencode from distinct `task` tool calls.
- Claude token counts are taken from `modelUsage` in the result event, which includes subagents; the top-level `usage` covers only the main agent. A call can write several result events (the agent stops, a background task wakes it, it stops again); their `modelUsage` and `total_cost_usd` are totals of the session so far, so only the last one per session counts (summing them counted such calls two or three times; verified on Claude Code 2.1.325). A call cut off before any result event is counted from the `usage` of its assistant messages, one per message id; it is marked `estimated` and its cost is unknown. Reports sum the phases that reported a figure and give `phases_without_tokens`, `phases_without_cost` and `phases_usage_estimated`; such sums are shown with `≥`.
- Provider limits: a call counts as refused when it left no valid handoff and its log shows a limit (Claude: `rate_limit_event` with status `rejected` or a 429 result; Codex and opencode: an error event mentioning a usage or rate limit; the Claude and Codex cases have been seen live). The wait runs until the reset time the CLI reports (Claude: `resetsAt`; Codex: "try again at 11:43 AM" or "try again in …" in the message, read in the container's UTC clock or the host's local clock with `--no-container`), plus one minute; when no time is given, 15 minutes plus one. Refused calls are listed in `state.rate_limits`, not in `events`; they use no retry and add no agent time. Waiting is excluded from the parallel track's elapsed time.
- Tasks: `task.json` holds `objective`, `acceptance_criteria` ("Must have"), `decisions`, `out_of_scope` and, for the UI tasks, `design_freedom` and `screenshots`, and for TASK-011, 012, 014, 015 and 016 `ecology_ideas` (optional suggestions, never a review criterion); `task.md` is the same content as prose and is what agents are told to read. A test keeps the two in step.
- Screenshots: `package` runs `./evosim ui --screenshots /shots` under `xvfb-run` (1920x1080) in the build container after a successful build, with a 180 s limit. Only regular files with a PNG signature, at most 8 MB each and six in total, are copied to the results folder; names are reduced to `[a-z0-9._-]`. A failure here does not affect `build_ok`.
- Browser in the image: Ubuntu 24.04 ships Chromium only as a snap, which does not run in a container, so the image installs Playwright's Chromium (pinned Playwright version) under `/opt/browsers` and a `chromium` wrapper that adds `--no-sandbox`. Evaluation containers derive from the same image, so the browser is also there when tests run without network. Rebuild with `python3 run.py build-image` after changing the Containerfile.
- Outages: a call without a valid handoff is an infrastructure failure when (a) Claude ends with `terminal_reason: api_error` and no status, a 5xx, 408 or 409 (401/403 count as a rejected login; other 4xx stay the model's result), (b) Codex or opencode end with a failed turn or a final error event that names a connection, server or login problem, (c) the model produced no output tokens and used no tool in the whole call, or (d) the harness ended the call because a `host_ports` server stopped answering (three checks 30 s apart). Claude's case was produced live by cutting the container's network; the Codex and opencode patterns are assumptions. Such calls are listed in `state.infra_failures`, their time and tokens are summed in `state.uncounted`, and they are neither events nor retries. `state.halt` holds the reason when the run stopped itself; it is cleared on the next start.
- Interruption: SIGTERM and SIGHUP are turned into `KeyboardInterrupt`; `cmd` kills the agent's process group on any exception, and `run` stops the container before its first phase because ending `podman exec` alone does not end the process inside. A phase commit that fails (for example on a full disk) is recorded as `commit_error` in the event and does not end the run; the files go into the next commit, and a parallel checkout is committed again before its merge. Git calls that stage or commit have a 15-minute limit.
- Uncounted work: time and tokens of calls that are repeated after a limit or an outage are summed in `state.uncounted` and shown as `uncounted_*` in reports; they are not part of agent time, tokens or cost. Work of a phase that was cut off by killing the harness is not measured at all; only the interruption is recorded. In all three cases the checkout is put back to the commit the phase started from (`git reset --hard`, `git clean -fd`; ignored build output stays), so the repeated phase cannot build on work that was not counted. The start commit is kept in `inflight*.json` as `head`. Files of a counted phase whose commit failed are kept.
- Final evaluation: when no task can go on any more, `run` scores the workspace HEAD once more with the label `final`, counting DONE and BLOCKED tasks as due (a blocked task's commits stay in the workspace; in the parallel track an unmerged checkout is not part of HEAD). This is the run's headline score; `evaluate` repeats it. Blocked tasks are reported in two kinds: `review` (the review still found gaps after the last cycle) and `error` (phases failed).
- Evaluation catch-up: at the start of `run`, every DONE task without a successful evaluation is scored at its own commit (last phase commit, or merge commit in the parallel track) with the tasks that were done at that time. `state.evaluations` is kept in completion order so the last entry stays the run's current score.
